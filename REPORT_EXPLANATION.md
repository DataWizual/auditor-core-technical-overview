# Auditor Core Enterprise Report Guide

**WSPM v2.2 — Extended Governance Edition**

This document explains every major metric, structural block, governance declaration, and analytical layer present in the HTML and PDF reports generated by Auditor Core Enterprise.

The objective is deterministic clarity:

* What the number represents
* How it is calculated
* What analytical layer it belongs to
* What it means for technical risk, governance, and compliance

---

# Report Architecture Overview

The report consists of five independent analytical layers:

1. Technical Detection Layer
2. AI Validation Layer
3. Risk Modeling Layer (WSPM v2.2)
4. Policy & Governance Layer
5. Compliance & Evidence Layer

Each metric belongs to exactly one of these layers.

# 1. Classification & Integrity Layer

## Confidentiality Banner

Indicates restricted distribution and intended audience.

Does not affect scoring.

---

## Report Integrity Verification

Report integrity is verified via SHA‑256 hash of normalized finding content.

Purpose:

* Tamper detection
* Audit defensibility
* Compliance reliability

This is a governance control mechanism, not a risk metric.

---

# 2. Enterprise Security Posture (Header Block)

## Project & Findings

Represents:

* Analyzed repository/application
* Total normalized findings after AI reconciliation

The count includes all severities, including AI‑excluded findings.

---

## Credibility (Score / 100)

Measures assessment reliability:

* Engine stability
* Data completeness
* AI validation consistency
* No pipeline corruption

Credibility measures report trustworthiness — not security strength.

---

# 3. Security Posture Index (SPI)

## Primary SPI

Range: 0–100
Higher = safer
Lower = higher exposure

Represents exponential risk normalization under WSPM v2.2.

---

## SPI Grade (Letter)

A single letter grade derived from the numerical SPI value.

| Grade | SPI Range | Label |
|-------|-----------|-------|
| A | 90–100 | Hardened |
| B | 75–89 | Strong |
| C | 60–74 | Needs Attention |
| D | 40–59 | Exposed |
| F | 0–39 | Critical Risk |

The label (e.g. NEEDS_ATTENTION) appears alongside the letter grade in the HTML report header.

Does not replace the numerical SPI — it is a human-readable summary only.

---

## Dual SPI Presentation (PDF)

Two values may appear:

1. Numerical SPI (pure WSPM output)
2. Policy‑adjusted presentation SPI

These represent different analytical layers and must not be conflated.

---

# 4. WSPM v2.2 Methodology

Model: Stabilized Multiplicative Risk with Dynamic K‑Factor.

Properties:

* Exponential exposure decay
* Dynamic sensitivity tuning
* Deterministic output
* Exposure stabilization via caps

---

# 5. SPI Formula

```
SPI = 100 × e-(Exposure / K)
```

Where:

* Exposure = Weighted Exposure
* K = Sensitivity factor

---

# 6. Weighted Exposure

Weighted Exposure is not a CVSS sum.

It incorporates:

* Severity weighting
* Context multiplier (Prod vs Test)
* Reachability scaling
* AI confirmation adjustment
* Chain escalation multiplier
* Exposure caps per rule category

---

## Exposure Capping

Each rule category has a maximum exposure contribution.

Purpose:

* Prevent noisy detector distortion
* Avoid single‑rule SPI collapse
* Maintain model stability

---

# 7. K‑Factor / K‑eff

Controls exponential decay sensitivity.

Higher K → slower score degradation
Lower K → faster score degradation

K‑eff may reflect post‑cap or production‑only recalibration.

---

# 8. Context Distribution

Core/Prod vs Test/Noise distribution.

Production findings:

* Fully weighted
* Included in SPI

Test findings:

* Visible in report
* Down‑weighted or excluded from SPI

---

# 9. Reachability Breakdown

Categories:

* Reachable
* Static‑Safe
* Unknown

Reachable findings retain full weight.
Static‑Safe findings are heavily down‑weighted.
Unknown findings receive partial weight.

---

# 10. AI Validation Layer

AI verdict types:

* SUPPORTED
* NOT_SUPPORTED
* INCONCLUSIVE

AI may:

* Confirm exploitability
* Reject false positives
* Provide architectural reasoning
* Identify attack paths

Only SUPPORTED findings increase exposure weight.

---

## AI Confidence Percentage

Displayed alongside each AI verdict (e.g. "AI VERIFIED (75%)").

Represents the internal confidence score of the AI validation engine for that specific finding.

* 100% — maximum confidence, finding fully confirmed or fully rejected
* 75–90% — high confidence with minor uncertainty
* 0% — AI has dismissed the finding as a false positive

The percentage is informational and does not directly modify the exposure weight; only the verdict (SUPPORTED / NOT_SUPPORTED / INCONCLUSIVE) determines weight adjustment.

---

## AI Verdict Display Labels (HTML)

The HTML report renders AI verdicts as visual badges:

* 🔥 AI VERIFIED — verdict is SUPPORTED; finding confirmed as exploitable
* 🛡️ AI FALSE POSITIVE — verdict is NOT_SUPPORTED; finding dismissed by AI
* ⚠️ REQUIRES REVIEW / no AI coverage — no AI verdict issued; manual review required

---

## AI Dismissed Findings

Findings where AI verdict is NOT_SUPPORTED are marked "AI DISMISSED — MANUAL REVIEW ADVISED" in the Evidence Appendix.

These findings remain visible in the report but are excluded from SPI exposure calculation.

Manual review is still advised because the AI lacked sufficient context in some cases (e.g. heavily obfuscated code).

---

## AI Excluded Findings

AI‑classified false positives remain visible but are excluded from SPI calculation.

This reduces false positive inflation.

---

## Attack Path (PATH field)

Each AI-analysed finding includes an attack path summary:

```
PATH: <source> ➔ <sink>
```

Examples:

* `user input ➔ eval function`
* `$target ➔ shell_exec`
* `hardcoded secret ➔ curl_exec`

This represents the adversarial data flow identified by the AI engine: from the entry point (source) to the vulnerable execution point (sink).

An empty PATH (➔ alone) indicates the AI could not identify a clear data flow, which may support a NOT_SUPPORTED verdict.

---

# 11. Per-Finding Fields

Each finding in the findings table contains the following fields:

## Severity

Classification level: CRITICAL, HIGH, MEDIUM, LOW, INFO.

Drives remediation priority and exposure weight. See Section 14 for distribution.

---

## Rule ID

Identifier of the detection rule that triggered the finding.

Examples present in reports:

* `SAST_COMMAND_INJECTION` — static analysis detection of command injection patterns
* `SAST_XSS` — static analysis detection of cross-site scripting patterns
* `generic-api-key` — secret detection: hardcoded API key or token
* `SECRET_GENERIC_SECRET` — secret detection: generic secret pattern match
* `GHA_UNPINNED_ACTION` — CI/CD analysis: GitHub Actions workflow using an unpinned action version
* `BANDIT_B101` — Python static analysis: use of `assert` statement (removed in optimised bytecode)

---

## Location

File path and line number of the finding.

Format: `path/to/file.ext:line` or `path/to/file.ext — N instances · lines X, Y`

Multiple instances at different lines within the same file may be grouped under one finding entry.

---

## Detector

The scanning engine that produced the finding.

Detectors present in reports:

* `SastScanner` — Static Application Security Testing engine (PHP, JS, Python)
* `GitleaksDetector` — Secret and credential leakage detection engine
* `SecretDetector` — Generic secret pattern matching engine
* `cicd_analyzer` — CI/CD pipeline configuration analysis engine (GitHub Actions, etc.)
* `BanditDetector` — Python-specific static analysis engine (Bandit)

---

## Description

Human-readable explanation of what the detector identified.

---

## CWE

Common Weakness Enumeration identifier for the vulnerability class.

`CWE-UNKNOWN` indicates the rule has not yet been mapped to a specific CWE entry. Does not affect scoring.

---

## CVSS

Numerical severity score assigned to the finding by the detection engine.

This is the raw detector score, not a standard CVSS Base Score computed from a full vector. It reflects the engine's internal risk weight for the rule category.

CVSS values do not directly equal exposure contribution — exposure is computed via WSPM v2.2 weighting (see Section 6).

---

## Compliance Mapping (per finding)

Each finding is individually mapped to applicable controls across:

* SOC 2 Trust Services Criteria (e.g. CC6.6, CC7.1)
* CIS Controls v8 (e.g. CIS-16.1, CIS-16.12)
* ISO/IEC 27001:2022 Annex A (e.g. A.8.26, A.8.28)

This enables direct traceability from finding to regulatory control.

---

# 12. Intelligence Engine (INTEL)

A secondary static reachability analysis layer that operates independently from the AI Validation Layer.

Displayed per finding as: `⚙️ INTEL: <status>`

## Intelligence Engine Status Values

* `UNKNOWN` — the static engine could not determine reachability; no external data found for the identified entity
* `POTENTIALLY_REACHABLE` — the identified entity (function, variable, endpoint) is assessed as publicly accessible via external call

## Intelligence Engine Conclusions

After combining the static reachability result with the AI verdict, the engine produces a conclusion:

* `INCONCLUSIVE: Static engine lacked sufficient context. AI verdict retained.` — static analysis was unable to resolve reachability; the AI verdict takes precedence
* `AGREED SAFE: AI and static analysis both indicate no exploitable path.` — both engines independently concluded the finding is not exploitable
* `[Chain CHAIN_XXXX context applied — confidence boosted.]` — chain membership has been applied as additional context, increasing confidence in the verdict

The Intelligence Engine status is informational and does not independently modify exposure. The AI verdict determines exposure adjustment.

# 13. Sensitivity Snapshot (Worst-Case Simulation)

Simulates worst‑case posture if all uncertain findings become exploitable.

Used for stress‑testing structural risk.

Not the current posture.

---

# 14. Chain & Attack Path Analysis

Critical chains link findings across files.

Chain effects:

* Escalated severity
* Increased exposure multiplier
* Systemic exploit modeling

Chains represent multi‑step adversarial reasoning.

# 15. Policy & Governance Layer

## Assessment Result

Possible outcomes:

* PASS
* WARN
* BLOCK
* FAIL
* REQUIRES REMEDIATION

This is policy‑driven and independent from numeric SPI.

---

## CORE_GATE_FAILURE

Indicates governance override triggered by production‑critical findings.

Numeric posture and governance verdict are separate analytical dimensions.

# 16. Severity Distribution

Raw finding counts by severity.

These values do not equal exposure contribution.

# 16a. Quick Analysis Filters

Interactive filter buttons present in the HTML report.

Allow filtering the findings table by severity:

* ALL — shows all findings regardless of severity
* CRITICAL — filters to critical findings only
* HIGH — filters to high findings only
* MEDIUM — filters to medium findings only
* LOW — filters to low findings only
* INFO — filters to informational findings only

Each button label shows the count of findings in that severity bracket.

This is a UI navigation feature only and does not affect scoring or compliance mapping.

## Compliance Coverage Dashboard

# 18. Remediation Roadmap

Structured guidance:

* CRITICAL → Immediate (0–3 days)
* HIGH → Current sprint (1–2 weeks)
* MEDIUM → Next release cycle
* LOW → Maintenance backlog

This is operational guidance, not a scoring artifact.

Report may support:

* SOC 2 readiness preparation

---

# 21. What Drives SPI Most

Highest impact factors:

1. CRITICAL findings in production
2. Reachable vulnerabilities
3. AI‑supported exploit chains
4. High exposure relative to K
5. Concentration in Core/Prod

Lowest impact factors:

1. Test‑only findings
2. Static‑safe code
3. AI‑excluded findings
4. Informational issues

---

# Final Interpretation Model

SPI answers:

> How exposed is this codebase structurally?

Chain analysis answers:

> Can findings combine into systemic exploit paths?

Compliance mapping answers:

> Which control domains are impacted?

Policy verdict answers:

> Is this acceptable under governance rules?

Integrity verification answers:

> Has this report been altered?

Each number and label in the report belongs to a clearly defined analytical layer. Understanding the report requires strict separation of those layers.
